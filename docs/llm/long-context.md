# 긴 문맥과 메모리

!!! spec "핵심 논문 · 연도"
    Beltagy 외, "Longformer" (2020) · Press 외, "ALiBi" (2021) · Su 외, "RoFormer (RoPE)" (2021) · Dao 외, "FlashAttention" (2022) · Chen 외, "Position Interpolation" (2023) · Peng 외, "YaRN" (2023) · Liu 외, "Ring Attention" (2023) · Xiao 외, "StreamingLLM: Attention Sinks" (2023) · Hsieh 외, "RULER" (2024)

!!! basic "한눈에 보기"
    초기 GPT는 한 번에 약 2,000토큰(A4 몇 장)밖에 읽지 못했습니다. 지금은 수십만–백만 토큰(책 여러 권, 코드 저장소 전체)을 한 번에 넣을 수 있는 모델이 있습니다(2026년 11월 기준).

    긴 문맥이 어려운 이유는 세 가지입니다.

    1. **계산**: 어텐션은 모든 토큰이 모든 토큰을 보므로, 길이가 2배면 계산은 약 4배입니다.
    2. **메모리**: 생성할 때 앞 토큰들의 Key·Value를 저장하는 **KV 캐시**가 길이에 비례해 커집니다. 긴 문맥에서는 모델 가중치보다 커지기도 합니다.
    3. **위치 감각**: 학습 때 본 길이보다 긴 글을 넣으면 위치 정보가 낯설어 성능이 무너집니다.

    또 하나, 긴 문맥을 **넣을 수 있다는 것**과 **잘 활용한다는 것**은 다릅니다. 긴 글 한가운데 숨은 정보를 놓치거나, 여러 군데 흩어진 정보를 종합하는 데 약한 경우가 있습니다.

## 문맥 길이의 발전 { .l2 }

| 시기 | 대표적 문맥 길이 |
|---|---|
| 2018–2020 (GPT-1·2·3) | 512–2,048 |
| 2023 | 8K–32K, 일부 100K–200K |
| 2024–2026 | 128K가 기본, 상용 모델 중 1M 이상도 등장 |

## 위치 인코딩 늘리기 { .l2 }

대부분의 LLM은 짧은 문맥(4K–8K)으로 사전 학습한 뒤, 마지막 단계에 긴 문서로 **문맥 확장 학습**을 합니다. RoPE를 쓰는 모델은 회전 각도를 조정해 더 긴 위치를 표현합니다.

| 방법 | 아이디어 |
|---|---|
| 위치 보간 (PI) | 위치 번호를 줄여(예: 1/4) 학습한 범위 안에 밀어 넣음 |
| NTK-aware 스케일링 | 고주파 성분은 유지, 저주파만 늘림 |
| YaRN | 주파수 대역별로 보간 정도를 다르게 + 어텐션 온도 보정 |
| RoPE 기저 증가 | 기저 θ(10,000)를 50만–수백만으로 키워 회전을 느리게 |

## KV 캐시 줄이기 { .l2 }

토큰당 KV 캐시 = \(2 \times L \times n_{kv} \times d_{head} \times\) 바이트 수 ([트랜스포머](../arch/transformer.md) 전문가 노트).

| 방법 | 줄이는 것 |
|---|---|
| GQA·MQA | KV 헤드 수 \(n_{kv}\) |
| MLA | K·V를 저차원 잠재 벡터로 압축해 저장 |
| KV 캐시 양자화 | 바이트 수 (FP16 → FP8·INT4) |
| 슬라이딩 윈도 어텐션 | 일부 층은 최근 W개 토큰만 봄 → 그 층의 캐시가 W로 고정 |
| 층 간 공유·하이브리드 | 일부 층만 전역 어텐션, 나머지는 SSM·선형 어텐션 |
| 토큰 버리기 (H2O, StreamingLLM) | 중요도가 낮은 토큰의 캐시를 삭제 (어텐션 싱크는 유지) |

## 긴 문맥 vs RAG { .l2 }

| 항목 | 긴 문맥에 통째로 넣기 | RAG (검색해서 일부만 넣기) |
|---|---|---|
| 준비 | 없음 | 문서 분할·임베딩·색인 필요 |
| 정보 누락 | 적음 (전부 넣었으므로) | 검색이 놓치면 답 못함 |
| 비용·지연 | 매 요청마다 긴 입력 처리 (프롬프트 캐싱으로 완화) | 짧은 입력 |
| 자료 규모 | 문맥 창 이내 | 사실상 무제한 |
| 종합 추론 | 문서 전체를 아우르는 질문에 유리 | 조각난 정보로는 어려움 |

실무에서는 둘을 섞습니다. 검색으로 후보를 넓게 가져오고, 긴 문맥에 넉넉히 넣습니다 → [RAG](../apps/rag.md).

## 코드로 보기 { .l2 }

모델 구성별로 문맥 길이에 따른 KV 캐시 크기를 계산합니다(FP16 기준, 요청 하나).

```python
def kv_cache_gib(layers, kv_heads, head_dim, tokens, bytes_per=2):
    return 2 * layers * kv_heads * head_dim * bytes_per * tokens / 2**30

configs = {
    "32층, MHA 32헤드 (7B급, GQA 없음)": (32, 32, 128),
    "32층, GQA 8헤드 (8B급)":           (32, 8, 128),
    "80층, GQA 8헤드 (70B급)":          (80, 8, 128),
}
for name, (L, h, d) in configs.items():
    sizes = [f"{kv_cache_gib(L, h, d, T):6.1f}" for T in (4_096, 32_768, 131_072, 1_048_576)]
    print(f"{name:30s} 4K/32K/128K/1M 토큰: " + " / ".join(sizes) + " GiB")

# 어텐션 점수 계산량은 길이 제곱에 비례
for T in (4_096, 131_072):
    print(f"T={T:>7,}: 어텐션 점수 행렬 원소 {T*T:.2e}개 (헤드·층마다)")
```

70B급 모델에 128K 토큰을 넣으면 요청 하나의 KV 캐시만 약 40 GiB입니다. 모델 가중치(FP16 약 140 GB)와 함께 GPU 여러 장이 필요한 이유이며, 동시 사용자가 많을수록 KV 캐시가 서버 메모리의 대부분을 차지합니다.

??? expert "전문가 노트 — 긴 문맥 평가, 링 어텐션, 학습 데이터, 메모리 구조"
    **평가의 함정.** "건초 더미에서 바늘 찾기(NIAH)"처럼 긴 글 속 문장 하나를 찾는 과제는 대부분의 모델이 거의 만점을 받아 변별력이 낮습니다. RULER(2024)는 여러 바늘, 변수 추적, 집계 같은 과제로 **유효 문맥 길이**를 재며, 광고된 길이보다 유효 길이가 훨씬 짧은 모델이 많음을 보였습니다. 실제 업무형 평가(긴 문서 QA, 코드 저장소 이해)로 확인하는 것이 좋습니다.

    **링 어텐션과 문맥 병렬.** 시퀀스를 여러 GPU에 나누고, K·V 블록을 링 모양으로 돌려 가며 FlashAttention처럼 블록 단위로 누적 계산합니다. 통신을 계산과 겹치면 GPU 수에 비례해 문맥 길이를 늘릴 수 있어 백만 토큰 학습의 기반이 됩니다.

    **긴 문맥 학습 데이터.** 긴 문서(책, 코드 저장소)를 이어 붙이고, 짧은 문서도 문서 경계를 넘어 어텐션이 새지 않도록 마스킹합니다. 긴 문서만으로 학습하면 짧은 문맥 성능이 떨어지므로 비율을 섞습니다. 장거리 의존성이 실제로 필요한 합성 과제를 넣기도 합니다.

    **문맥 밖의 메모리.** 대화가 아무리 길어도 문맥 창은 유한합니다. 에이전트는 오래된 대화를 요약하거나, 중요한 사실을 외부 메모리(파일, 벡터 DB)에 저장하고 필요할 때 다시 불러오는 방식으로 "장기 기억"을 구현합니다 → [에이전트와 도구 사용](../apps/agents.md).
